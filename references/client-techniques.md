# 客户端实现经验

这些结论来自一次 Unity WebGL/IL2CPP 小游戏研究。用于定位问题，不是其他游戏的已验证事实。

## WASM 与元数据

先检查模块类型、导入/导出、函数符号、IL2CPP 元数据和配置。原文件不可变，补丁以 SHA-256 限定版本；只添加必要导出和小范围入口 hook，避免破坏原索引。核对整数、浮点、返回值和结构体 ABI，分配内存在 finally 释放。补丁生成后验证模块并实际进入游戏；不要把某次版本的内存地址写成跨游戏规则。

大体积 WAT 或单行函数 JSON 不应直接整行搜索输出。按函数头流式截取 WAT，或解析 JSON 后筛选字段，防止数百 MB 输出吞没上下文。

## 战斗与时间

- 锁血仅作用于玩家受击；伤害倍率仅放大玩家造成的正向伤害。识别召唤物或不同攻击路径时另行验证，不默认全部已覆盖。
- 收获倍率只作用于正向增量，不修改消耗、绝对赋值、独立装备对象或手动发放量。
- 无限钥匙/局内货币只在低于目标时补足，禁用和后台时不查询或写入无关状态；界面关闭不刷新显示。
- 在本次游戏中，返回城镇后 gameplay 指针仍可能存在。实际战斗要结合战斗 UI/生命周期状态判定，不能以非零指针为唯一依据。
- 原倍速按钮标签可能是近似值。更高倍率应接入原速度 setter，尊重暂停的零值、恢复和城镇切换，不每帧强写。修改器覆盖时说明哪个控件优先，提供恢复原生控制选项。
- 素材时间和战斗时间分离；本地时间偏移持久化，不改系统时钟。是否后台累计按用户需求明确实现，不能意外把暂停时间算入。

## 装备、资源和清理

原生配置决定部位、型号、品质、加阶和强化等级：名称相似不代表同一类对象。橙色 +3 精华与橙色 +3 成品可能属于不同配方入口。先证实结构和真实合成行为，再做 UI。

强化可能按部位共享，装备个体则按型号/品质计数；不能直接承诺“某一把”的等级变化。支持六部位等完整范围时从配置枚举，不从用户举例推断只做武器。最高品质、强化上限均从配置验证。

清理方案先读取已持久化库存，确认字段、编码和计数合法。预览指纹包含部位、门槛及对象/数量；背包变更后旧确认失效。使用原删除接口按栈批量处理，保存读回；测试门槛本身保留、穿戴保留、材料保留、重启一致及撤销恢复。

## 性能与存档验证

变化才写控制项，低于目标才补资源，可见才更新文本；这些可以先于降低画质优化。必要时记录调用次数证明减少重复工作，但 FPS 改善必须通过可比较的实际场景验证。

存档解析用于诊断和预览时应验证头部、长度和编码；优先通过原业务接口写入。恢复备份后重启前设置跳过旧页面保存，避免 onPause/unload 把旧状态写回。不要把合成测试存档或用户存档放到共享技能中。
